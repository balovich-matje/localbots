# Can Localbots add a PvP-gear Droptimizer source? — Verdict: buildable now, non-functional until simc's Live item DB catches up

## TL;DR
- **Enumerating the current PvP set from wago = FEASIBLE and easy**, but NOT via the "Pvp*" tables. The set lives in `ItemSparse` and is found by item-name prefix.
- **Simming it in the app = currently BLOCKED** by an external data lag: the user's simc Live build (68887) simply does not contain the current PvP set, so every piece fails with `Cannot initialize data`. This is a timing gap, not a design wall — all *prior* PvP seasons are in simc, and this season's set is already in simc's PTR DB.
- The app degrades gracefully today (existing probe/`available` machinery flags the source unavailable), and self-heals when simc's Live data updates.

## Task 1 — Which wago tables enumerate the PvP set? (None of the obvious ones)
Fetched live with the same `https://wago.tools/db2/{Table}/csv` pattern `server/wagoData.js` uses:
- **PvpSeason** `ID,MilestoneSeason,AllianceAchievementID,HordeAchievementID` — 28 rows, latest ID 40 (MilestoneSeason 106). No item ids.
- **PvpTier** — rating brackets (Combatant/Challenger/Rival/Duelist…). No items.
- **PvpScalingEffect** `ID,SpecializationID,PvpScalingEffectTypeID,Value` — the per-spec PvP-*combat* stat template. Useful only as confirmation that PvP scaling is a combat-context effect, not gear metadata.
- **PvpSeasonRewardLevels** `ID,Tier,EndOfMatchILvl,WeeklyCacheILvl,PvpSeasonID` — **stale**: highest `PvpSeasonID` is 14 (ilvls 200–226). Unusable for the current season.
- **PvpItem** and **PVPItem** (the real `ItemID -> ItemLevelDelta` table) → **HTTP 404 "Table not found"**. wago does not export it. So there is no clean per-item PvP flag or PvP-ilvl source on wago.

I also checked the `ItemNameDescription` route (ItemSparse col 69 `ItemNameDescriptionID`): older PvP gear referenced "Season N" descriptors, but **all modern PvP gear has `ItemNameDescriptionID = 0`** (the season prefix is baked into the display name). Dead end for current gear.

## Task 2 — Getting the item ids + ilvls (works, from ItemSparse by name prefix)
The current set is fully present in the already-cached `ItemSparse.csv`, distinguished by name prefix + `ExpansionID==11`:
- **Conquest**: `"Venomous Gladiator's …"` — **288 equippable items, ItemLevel 298, quality 4 (epic)**.
- **Honor**: `"Venomous Aspirant's …"` — **106 equippable items, ItemLevel 259, quality 3 (rare)**.

Sample ids: 270853 Greatblade (inv17 2H), 270563 Cloak (inv16, stats 71/7/40/32), 277951 Aspirant's Slicer (inv13), 270445 Aspirant's Shield (inv14), 280118/280097 Aspirant's Medallion/Insignia (inv12 trinkets). Full slot + class coverage, real stats, real `AllowableClass` and `Item.ClassID/SubclassID` — so **`server/lootFilter.js` `usableSlots()` filters them correctly with no changes** (armor type, weapon proficiency, primary stat, quality≥3 all already handled; ilvl-1 tokens fall out because their `InventoryType` is 0).

The naming model is stable across seasons (last season = `"Prized Gladiator's"`, ExpansionID 10, ilvl 584), so the per-season anchor is just the two prefixes — curate them like everything else in `season.json`.

**Caveat on ilvl:** the 298/259 in ItemSparse are the item's PvP/base-record numbers, not a PvE item level. There is no clean wago source for the *PvE* ilvl of PvP gear (PvpSeasonRewardLevels stale, no PvpItem). A sensible PvE ilvl must be hand-curated per season, exactly like the existing `season.json` `worldBossIlvl` / `delveTracks`.

## Task 3 — How simc treats PvP gear in a PvE sim (verified)
Because these items are absent from the Live 68887 DB, I verified against simc's **PTR** DB (`ptr=1`, build 12.1.0.68914) which contains them (this is only a measurement harness — see the blocker; ptr=1 is not a shippable workaround):
- **Bare `main_hand=,id=270853`** (no ilevel) → `json2` `player.gear.main_hand.ilevel = 62`. The item *downscales* in PvE with no bonus/ilevel; it does NOT sim at 298.
- **With explicit ilevel** → resolves to exactly the passed value, no PvP delta added: `259→259` (str 1617), `289→289` (str 2326), `298→298` (str 2579).

This is the good news for the pipeline: `server/droptimizer.js` `addItem()` **always** writes `id=X,ilevel=Y`, and `server/simcProbe.js` probes at `ilevel=272`. Both use the explicit-ilevel path, which resolves cleanly with no PvP scaling. So on any simc build that *has* the items, the app sims them correctly at whatever curated PvE ilvl we choose.

## The real blocker (why it's "mixed", not "easy")
On the user's Live build 68887, `main_hand=,id=270853` → `Initialization error: Item 'inactive' Slot 'main_hand': Cannot initialize data.` `grep` of `~/tools/simc-src/engine/dbc/generated/item_data.inc` (Live): **0** hits for "Venomous Gladiator"/"Venomous Aspirant" and 0 for the ids — yet **16554** "Gladiator" hits overall, and last season's `Prized Gladiator`=299, `Crimson Gladiator`=294, `Obsidian Gladiator`=290, `Prized Aspirant`=95. So simc normally includes PvP vendor gear; only *this* season's set is missing from the Live 68887 extract. It is already in `item_data_ptr.inc` (309/106 lines). The filter is item-precise: Haranir PvE items 270430–270444 are kept, the PvP block from 270445 on is dropped.

Consequence today: if shipped, `simcProbe` marks every PvP piece unknown → `buildSourceTree` sets the PvP source `available:false` / 0 usable → it renders greyed out, same as unreleased content. Correct and harmless. It lights up automatically once a future simc `git pull` + rebuild picks up the set in the Live extract (the header "Simc light" already messages build-lag).

## Slotting it in (medium effort, mirrors the Delves pattern)
- **`server/wagoData.js` `buildLootDb`**: PvP gear isn't in `JournalEncounterItem`, so enumerate it like the curated **Delves** pool. Add a `data/pvp-loot.json` (or `season.json` `pvp` block) with the two name prefixes + curated PvE ilvl per track; resolve prefixes→items the same way `delveNames` is resolved today; emit `{instanceId:'pvp', kind:'pvp', bosses:[{Conquest…},{Honor…}]}`.
- **`server/droptimizer.js`**: add a `source.kind==='pvp'` branch in `buildDroptimizerInput` (clone of the `'delves'` branch — read `selection.pvp={conquest,honor}`, look up `season.droptimizer.pvpTracks[track]`, call `addItem(item, ilvl, …)`), and a `tree.pvp` bucket + `else if (source.kind==='pvp')` in `buildSourceTree`. `countUsable`/`usableSlots` unchanged.
- **`server/lootFilter.js`**: no changes.
- **`server/simcProbe.js`**: no changes.
- Plus the small UI wiring for a PvP section and its two toggles (Conquest/Honor), matching the Delves UI.

## Recommendation
Data + wiring are a clean, low-risk medium job that reuses the Delves plumbing verbatim. But it should not ship as a live feature until simc's Live item DB includes the Venomous set — otherwise it's a permanently-greyed source. Two viable orders: (a) implement now and let the existing "unavailable" UX carry it until simc updates, or (b) wait for the next simc Live build to confirm the set is present, then implement. Either way, the one genuine design decision to settle first is the **curated PvE item level** for Conquest/Honor (no clean data source; Wowhead usable only as a human sanity-check).
